Laporan Security & Vulnerability Audit

Aplikasi SaaS Klinik Kecantikan — Ayumi Beauty House (multi-cabang / multi-tenant)
Tanggal: 18 Agustus 2026 Metode: Black-box, sisi browser (read-only) Target: localhost:3000 + Supabase dtrgxgutcuznrxflmpzk Sesi uji: Owner (kimadamaid@…)

Ringkasan Eksekutif

Audit menemukan satu kerentanan Critical yang berdampak langsung pada seluruh poin fokus Anda: tabel patients tidak dilindungi Row-Level Security (RLS). Akibatnya 3.961 rekam pasien — berisi nama lengkap, nomor WhatsApp, tanggal lahir, alamat, jenis kelamin, Instagram, tipe kulit, keluhan kulit, alergi, dan catatan medis — dapat dibaca oleh siapa pun tanpa login, hanya dengan API key publik yang memang tertanam di aplikasi. Data ini bocor lintas seluruh cabang (Ciamis + Banjar terbukti), sehingga sekaligus melanggar isolasi multi-tenant.

Kabar baiknya: mayoritas tabel lain (transactions, appointments, branches, users, treatment_records/SOAP, patient_photos, patient_coupons) sudah dilindungi RLS dengan benar, service_role key tidak bocor di bundle, dan tidak ditemukan pola XSS di kode aplikasi. Masalah utamanya terkonsentrasi dan bisa diperbaiki cepat.

Detail Temuan & Rekomendasi

F-01

Tabel patients tanpa RLS — PII & rekam medis bisa di-scrape publik

Critical
Dampak: Kebocoran massal data pribadi & medis 3.961 pasien; risiko pelanggaran UU PDP, pemerasan, phishing/penipuan ke pasien, kerusakan reputasi klinik.

Dengan hanya API key anon (yang memang publik dan tertanam di setiap bundle JS) dan tanpa autentikasi sama sekali (tanpa header Authorization), permintaan langsung ke PostgREST mengembalikan seluruh isi tabel patients:

GET https://dtrgxgutcuznrxflmpzk.supabase.co/rest/v1/patients?select=*
Header: apikey: <ANON_KEY>         (TANPA Authorization / tanpa login)

→ 200 OK   Content-Range: 0-0/3961
Kolom terekspos: full_name, whatsapp, birth_date, gender, address,
instagram, skin_type, skin_concerns, allergies, medical_notes, ...

Tabel pembanding pada proyek yang sama menolak permintaan anon (mengembalikan 0 baris), membuktikan RLS mereka aktif dan hanya patients yang salah konfigurasi:

TabelAnon (tanpa login)Owner (login)Status RLS
patients3961 baris3961JEBOL
transactions044Aman
appointments032Aman
treatment_records (SOAP)03971Aman
branches / users04 / 11Aman
Rekomendasi (segera):
  • Aktifkan & FORCE RLS pada tabel: ALTER TABLE public.patients ENABLE ROW LEVEL SECURITY; ALTER TABLE public.patients FORCE ROW LEVEL SECURITY;
  • Hapus policy permisif apa pun (mis. USING (true) atau policy untuk role anon). Buat policy scoping per-cabang, contoh: 
    CREATE POLICY patients_branch_select ON public.patients
FOR SELECT TO authenticated
USING (
  branch_id IN (
    SELECT branch_id FROM public.users WHERE auth_id = auth.uid()
  )
  OR EXISTS (SELECT 1 FROM public.users WHERE auth_id = auth.uid() AND role = 'owner')
);
  • Terapkan pola policy yang sama untuk INSERT/UPDATE/DELETE (WITH CHECK), jangan hanya SELECT.
  • Audit ulang seluruh tabel proyek: jalankan pengecekan tabel mana yang rowsecurity=false di pg_tables.
  • Karena data sudah pernah terekspos publik, perlakukan sebagai insiden kebocoran: catat, evaluasi kewajiban notifikasi sesuai UU PDP.
F-02

Isolasi multi-tenant / antar-cabang jebol pada data pasien

High
Dampak: Staf/terapis satu cabang (atau pihak tak berwenang) dapat membaca pasien seluruh cabang lain — melanggar prinsip pemisahan data cabang.

Query anon tunggal tanpa filter mengembalikan pasien dari lebih dari satu cabang, membuktikan tidak ada penyekatan tenant di lapisan data:

Sebaran patients per cabang (via anon, tanpa login):
  Ayumi Ciamis .......... 3960 baris  → terbaca
  Ayumi Banjar .......... 1 baris     → terbaca
  (query tanpa branch_id filter → semua cabang keluar)

Karena akarnya sama dengan F-01 (RLS patients mati), konsekuensinya: role therapist/admin cabang mana pun otomatis bisa membaca pasien cabang lain. Penyekatan cabang saat ini hanya diandalkan pada filter di sisi client (UI), bukan di server.

Rekomendasi:
  • Perbaikan F-01 sekaligus menutup ini: policy RLS wajib mem-filter branch_id berdasarkan cabang milik user (dari tabel users), bukan berdasarkan parameter yang dikirim client.
  • Jangan pernah mengandalkan .eq('branch_id', …) di kode client sebagai batas keamanan — itu hanya filter tampilan, bukan otorisasi.
  • Uji lanjutan: login sebagai therapist cabang Banjar, lalu coba GET patients?branch_id=eq.<Ciamis> — setelah RLS benar, hasilnya harus kosong.
F-03

Integritas transaksi kasir & komisi dihitung/dipercaya di sisi client

Medium
Catatan: Tidak diverifikasi tuntas karena audit dibatasi read-only; dinilai dari arsitektur data yang teramati. Bisa naik ke High bila penulisan tidak divalidasi server.

Dashboard menarik komponen harga mentah ke client dan menjumlahkannya di browser:

GET /rest/v1/transactions?select=id,branch_id,total,payment_method,
    transaction_items(item_type,name,quantity,subtotal,
                      original_price,discount_percent)

Bila policy RLS untuk INSERT/UPDATE pada transactions/transaction_items mengizinkan user authenticated menulis nilai discount_percent, subtotal, total, atau komisi/sisa sesi kupon secara langsung, maka kasir/terapis dapat memanipulasi angka (mis. menambah diskon, mengecilkan total, menaikkan komisi) lewat panggilan API langsung — melewati UI.

Rekomendasi:
  • Hitung ulang total, diskon, dan komisi di server (Postgres function / RPC / Edge Function), jangan percaya nilai kiriman client.
  • Batasi kolom yang boleh ditulis client; jadikan total, subtotal, komisi sebagai generated/derived atau diisi oleh trigger, bukan input bebas.
  • Terapkan batas discount_percent (0–maksimum kebijakan) via CHECK constraint + policy WITH CHECK; catat siapa yang memberi diskon (created_by) untuk audit.
  • Kurangi sisa sesi kupon lewat transaksi atomik server-side agar tidak bisa di-replay/diperbanyak dari client.
  • Uji tulis (di lingkungan staging) untuk memastikan manipulasi ini benar-benar tertolak.
F-04

RBAC bergantung tabel users; JWT tidak memuat klaim role/branch

Medium
Dampak: Otorisasi rawan jika hanya diperiksa di UI/route; potensi privilege escalation bila policy pada users longgar.

JWT sesi tidak memuat role aplikasi maupun branch_id — hanya role Postgres standar authenticated:

app_metadata: { provider: "email" }   // tidak ada "role", tidak ada "branch_id"
role: "authenticated"

Role sebenarnya (owner / admin / therapist) dan branch_id disimpan di tabel users. Ini valid, tetapi menimbulkan dua risiko:

  • Halaman khusus owner (/settings/users, /settings/branches, /reports/therapists) harus dijaga oleh RLS di setiap tabel, bukan sekadar sembunyi di UI. Route guard di client dapat di-bypass via DevTools / panggilan API langsung.
  • Jika policy pada tabel users mengizinkan user meng-UPDATE baris sendiri termasuk kolom role, seorang therapist bisa menaikkan dirinya jadi owner (privilege escalation). Kolom role, branch_id, email, phone seluruh staf juga terlihat oleh sesi login — perlu dipastikan scoping-nya.
Rekomendasi:
  • Pindahkan role & branch ke custom JWT claims (via Auth Hook / app_metadata yang hanya bisa diubah service_role), sehingga RLS bisa membaca auth.jwt()->>'role' tanpa subquery dan tidak bisa dipalsukan client.
  • Pada tabel users: policy UPDATE harus melarang perubahan kolom role & branch_id oleh non-owner (gunakan WITH CHECK membandingkan nilai lama vs baru, atau kolom sensitif diubah hanya lewat RPC ber-otorisasi).
  • Verifikasi RLS untuk owner-only pada tabel users, branches, laporan komisi terapis — uji dengan sesi therapist yang mencoba GET data lintas cabang.
F-05

Token sesi Supabase tersimpan di cookie non-httpOnly (terbaca JavaScript)

Medium
Dampak: Bila terjadi XSS, penyerang bisa mencuri access_token/refresh_token → pengambilalihan akun penuh.

Cookie sb-dtrgxgutcuznrxflmpzk-auth-token terbaca penuh via document.cookie (bukan HttpOnly). Ditemukan pula cookie sisa dari proyek Supabase lain (sb-hrtgqpvfbksnycmtwijp-auth-token) yang sebaiknya dibersihkan. Ini adalah perilaku default @supabase/ssr, namun tetap memperbesar dampak bila ada celah XSS (F-06).

Rekomendasi:
  • Gunakan pola SSR yang menaruh token di cookie HttpOnly + Secure + SameSite=Lax/Strict dan lakukan refresh di server, sehingga token tidak terjangkau JS.
  • Terapkan Content-Security-Policy ketat untuk membatasi eksfiltrasi bila XSS terjadi.
  • Bersihkan cookie proyek Supabase yang tidak terpakai.
F-06

XSS pada input rekam medis & nama pasien

Low

Pemindaian seluruh bundle (28 chunk) tidak menemukan dangerouslySetInnerHTML pada kode aplikasi — kemunculannya hanya di pustaka framework (Next.js, Recharts). Karena React meng-escape teks secara default, XSS tersimpan lewat nama pasien / catatan SOAP kecil kemungkinannya saat ini.

Rekomendasi (pencegahan):
  • Pertahankan larangan dangerouslySetInnerHTML untuk data yang berasal dari input pengguna.
  • Waspadai konteks non-React: pembuatan link wa.me, ekspor "Cetak Laporan"/PDF, atau href dinamis — sanitasi & validasi nomor WA/URL.
  • Validasi input di server (panjang, karakter) untuk full_name, medical_notes, complaints.
F-07

Pemeriksaan kebocoran kunci — HASIL AMAN

Aman

Pemeriksaan network tab & seluruh bundle JavaScript:

  • SUPABASE_SERVICE_ROLE_KEY tidak ditemukan di bundle maupun network — tidak ada kebocoran kunci istimewa. (String "service_role" yang muncul hanya bagian dari pustaka @supabase/auth-js, bukan kunci nyata.)
  • Hanya anon key yang terekspos — ini memang publik dan wajar, selama RLS benar (lihat F-01).
  • Tidak ada storage bucket yang terkonfigurasi (fitur foto treatment belum terisi) — belum ada eksposur file publik saat ini.

Catatan: keamanan anon key sepenuhnya bergantung pada RLS. Selama F-01 belum diperbaiki, kunci publik ini adalah pintu menuju seluruh data pasien.
